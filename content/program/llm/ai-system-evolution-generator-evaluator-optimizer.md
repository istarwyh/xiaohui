## 一

第 8 集里，男主在医院走廊连续出现三次。

第一镜还是黑色外套，第二镜变成灰色风衣，第三镜脸型也换了。剪辑台上看得很清楚，角色已经不是同一个人。这个问题当然可以修。补参考图，改几句 `prompt`，锁 `seed`，重跑第二、三镜，运气好一点，当前这一集就能交出去。

麻烦在下一集。

如果下一集又回到医院、走廊、半身近景、同一角色连续出现，系统还会不会把衣服换掉？如果还会，那上一轮返工只是在救片子，没有改系统。

我不太看它重跑多少轮，而看返工有没有搬位置。只修当前镜头，我会把它放在闭环优化里。下次开工前，分镜表、角色卡、反例库和检查脚本多了一点内容，才像进化。如果几部作品都在视频层救同一种漂移，就该先考虑把返工往前挪，挪到剧本、分镜或资产准备阶段。

一个镜头从坏变好，不稀奇。我会追另一个细节，这次错误有没有进入下一次任务的输入条件里。

## 二

把医院走廊这个事故拆开，能看到三个动作。

先产出候选。它可能是一个 `LLM`，也可能是分镜生成器、图像模型、视频模型、检索器、代码生成器，或者一个会调用工具的 `Agent`。它不负责保证每次正确，它先把可选项拿出来。

再看哪里坏了。它不能只给一个 7.5 分，也不能只说「不像」。它要把问题拆成可处理的信号。脸漂了，衣服漂了，上一镜头的动作没接上，或者平台尺度不允许这个镜头出现。

最后决定改哪里。这一步最容易被含糊带过。是视频层重跑，还是补角色参考图？是缩短镜头，还是把多人同框拆成两个单人镜头？是改 `prompt`，还是承认资产层没有给够角色状态？

很多系统看起来有 `Loop`，实际只是反复再试一次。它能把当前产物磨到能看，但很难让下一次少犯同类错误。

生成器、评估器、优化器不是白板上的三个圆圈。它们决定这一次修改停在当前镜头，还是会回到分镜表、角色卡和检查脚本里。

![生成器、评估器、优化器形成反馈回路](https://xiaohui-zhangjiakou.oss-cn-zhangjiakou.aliyuncs.com/image/20260706-ai-system-evolution-generator-evaluator-optimizer.png)

## 三

闭环优化最容易被看见，也最容易被误认成进化。

女主第二个镜头的校服从蓝白变成红黑，评估器标记「角色一致性失败」，优化器补一张参考图，改几句 `prompt`，生成器重跑。镜头修好了。

这样的 `Loop` 有用。代码能跑测试，报告能过校验，图片能过审，视频能播出来，都离不开这一层。

可这次修复停在当前镜头里。下一集再遇到夜晚便利店、冷光源、半身近景、同一角色连续出现，系统可能继续把衣服换掉。人又要在同类镜头上花一次时间，分镜表和角色卡还是老样子。

闭环优化能让今晚的版本过审，却不等于明天的分镜表会多一列。判断时不要看这一轮重跑后是不是变好，而要看重跑原因有没有穿过当前产物，进入角色卡、分镜模板、检查脚本或者工具默认值。

## 四

修改意见如果只留在这一轮对话里，下一次生成时就不在输入里。这条意见要继续起作用，位置要换到分镜模板的服装状态、角色卡、反例库，或者检查脚本里。

还是角色漂移。如果系统只重跑，这叫修图。如果系统把这次失败归档为「同场戏角色状态漂移」，在分镜模板里加上服装、情绪、上一镜头动作，给角色卡补三视图和服装状态，再把坏样例放进反例库，下一次开工的条件就变了。

留下来的材料往往很普通。它可能是一份模板，一个资产库，一个回归样例，一个评分维度，一个工具默认值，也可能是一个 `skill`。

和我在 [[Claude Code Skill 不过是一个文件夹？]] 里说的一样，很多时候 `skill` 就是文件夹、规则、脚本和参考材料的组合。这个组合能把一次临时手法，改成下一次可以复用的用法。

```text
连续角色镜头生成 `skill`
  -> 输入角色卡、角色状态表、场景、分镜
  -> 先锁服装、情绪和光源
  -> 再生成静帧
  -> 再做视频
  -> 检查脸、衣服、姿态、动作延续
  -> 失败时局部重跑、拆镜头，或者退回资产层
```

这时，过去的失败不再只是返工成本。下次分镜时，它会先出现为一栏字段或一条检查规则。

![闭环优化、进化、自进化的三层关系](https://xiaohui-zhangjiakou.oss-cn-zhangjiakou.aliyuncs.com/image/20260706-ai-system-evolution-levels.png)

## 五

自进化难一点，因为它不是多存几条例子。

人批注「第二镜衣服错了」，系统补参考图，这很好。但如果它每次都把问题推到视频层重跑，就会越来越熟练地做一件昂贵的事。

更麻烦的是另一类反馈。把几部作品里人工改过的镜头列出来，常常会看到角色漂移集中出现在「跨场景切换后返回同一角色」。这时再补一张参考图只是止血。更该问的是，为什么角色状态总是拖到视频层才被发现？

线索在前面几张表里。剧本改分镜时没有角色生命周期表，资产层没有记录服装变化，分镜层没有要求上一镜头动作，视频层只好靠参考图硬救。优化器不能只重跑镜头，它要在剧本和分镜之间加一张角色生命周期表，再用后续项目比较有表和无表的返工率。

元评测如果只把评分器校准到这批样本上，下一批样本一换，分数又可能漂。回头看校准记录时，还要分清哪类改动长期有效，哪类只是堵住一次 `hack`。如果一次误判暴露出职责混在一起，那就拆出事实一致性、用户意图满足、交付格式三个检查，不要在旧评分器后面再贴一条规则。

## 六

漫剧麻烦在于，前面漏掉的问题不会停在一张图里。

剧本里一句「他突然崩溃」，如果没有被改成可拍的动作，分镜会虚。分镜虚，静帧就靠猜。静帧靠猜，视频层会用奇怪的表情和动作补空白。最后剪辑看到的是脸漂、动作断、情绪接不上，但病根可能在剧本层。

一部漫剧从剧本到成片，通常要穿过一条长链路：

```text
`IP` / 选题
  -> 剧本改编
  -> 故事蓝图
  -> 角色、服装、场景、道具资产
  -> 分镜 / 故事板
  -> 静帧 / 参考生视频
  -> 视频生成与选片
  -> 配音、音效、字幕、剪辑
  -> 发布
  -> 数据复盘
```

公开资料里，小云雀这类短剧 `Agent` 产品已经能从标准剧本进入故事蓝图、角色设计和分镜，并让人继续编辑角色与分镜。`Vidu` 这类视频模型把「参考生视频」和主体库放到更靠前的位置，用多参考素材维持角色和场景连续性。腾讯云开发者社区的行业文章也把漫剧制作拆成剧本、分镜、素材、视频生成、后期剪辑和发行运营等环节。[^xiaoyunque] [^vidu] [^tencent-cloud]

这已经不是「写一句提示词，生成一集」。

![AI 漫剧从剧本到剪辑的生产链路](https://xiaohui-zhangjiakou.oss-cn-zhangjiakou.aliyuncs.com/image/20260706-ai-comic-drama-production-pipeline.png)

这条线里，昂贵的是发现问题太晚；重跑一次模型只是表面成本。

## 七

把漫剧链路拆开后，要记录失败之后改了哪张表、哪个字段、哪条检查，不再只记「又重跑了一次」。

| 环节 | 常见失败 | 可写入的改动 |
| --- | --- | --- |
| 剧本 | 心理活动太长，画面承载不了 | 可视化改写规则，复杂群像拆镜头规则 |
| 资产 | 角色跨镜头漂移，服装状态不稳 | 角色卡、三视图、表情表、服装状态表 |
| 分镜 | 情绪接不上，角色位置跳，镜头太复杂 | 上一镜头动作字段，固定镜头词，高风险镜头标记 |
| 视频 | 脸部漂移、闪烁、口型错、动作断 | 参考图策略、镜头时长上限、关键帧和运动幅度约束 |
| 发行 | 前三秒留不住，封面误导，字幕节奏拖 | 开头冲突模板，封面检查项，剪辑节奏回归样例 |

这张表少一点口号。它回答的是下一次谁先看见问题，谁有权把问题退回上一层，谁负责把规则写进资产或模板。

生成器、评估器、优化器仍然在场，只是不必每段都把它们喊出来。谁产出，谁验收，谁决定返工位置，这些决定比三个名词更靠得住。

## 八

回到医院走廊那个事故。

最低成本的处理，是补参考图、改 `prompt`、锁 `seed`，把第二、三镜修好。片子能交，但下一次仍然可能掉进同一个坑。

更好的处理，是把它归档为「同场戏角色状态漂移」，在分镜模板里补服装状态字段，建立医院走廊场景的固定镜头词，把失败镜头放进反例库。下一次同场戏生成前，系统先检查角色状态。

再往前一步，是把多部作品里人工改过的镜头放在一起看。如果漂移总发生在「跨场景切换后返回同一角色」，旧策略就太依赖视频层重跑。此时加一条更长的 `prompt` 没有多少用，可以先在剧本到分镜之间加一张角色生命周期表，再比较它是否真的降低返工率。

漫剧只是把这件事放大了。保险报告、代码生成、投研分析、客服问答也一样。生成器负责尝试，评估器负责看见，优化器负责改变。

判断一个 `AI` 生产系统有没有进化，不要先看它用了多少模型，也不要先看它能不能连续跑多少轮。看下一次开工时，分镜表里有没有多出那一列，审核脚本有没有多跑一条检查，返工率有没有被拿出来比较。
