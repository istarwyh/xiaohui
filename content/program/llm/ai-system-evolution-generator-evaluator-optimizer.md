一条返工记录比定义更诚实。

女主第二个镜头的校服从蓝白变成红黑，评估器标记“角色一致性失败”，优化器补了一张角色参考图，视频生成器重跑。这个镜头修好了。系统有没有进化？还没有。它只是把这一帧从坏图修成了可用图。

如果下一次遇到夜晚便利店场景，系统会自动要求先锁定角色服装、光源、镜头词和参考图，再生成连续镜头，事情就变了。那次返工没有停在对话里，而是留下了新的资产规范、检查点和 `skill`。这才开始像进化。

再往前一步，如果系统发现“角色漂移”经常不是出图模型的问题，而是分镜阶段没有记录角色状态，于是主动在剧本到分镜之间加一张角色状态表，并用后续项目验证这张表确实降低返工率，这就接近自进化了。

## 三个对象

我更愿意把一个 `AI` 系统拆成三个对象看。

| 对象 | 它做什么 | 常见形态 |
| --- | --- | --- |
| `Generator` 生成器 | 提出候选产物 | `LLM`、图像模型、视频模型、检索器、代码生成器、分镜生成器、`Agent` |
| `Evaluator` 评估器 | 把“好不好”变成可观察信号 | 规则、测试、`LLM Judge`、人工审核、线上指标、领域专家评分 |
| `Optimizer` 优化器 | 把评估信号变成改动 | 改 `prompt`、重跑模型、调整资产、改流程、补测试、更新 `skill` |

生成器不只是模型。它还包括上下文装配、工具调用、素材检索、模板选择和任务拆解。评估器也不只是打分，它要决定系统能看见哪些问题。优化器更不是“再试一次”，它决定系统是修一处裂缝，还是改一段管道。

最小链路长这样：

```text
生成器 -> 产物与轨迹 -> 评估器 -> 反馈信号 -> 优化器 -> 改动 -> 生成器
```

这个图只说明系统有 `Loop`，还不能说明系统有进化。差别在于改动有没有留下来，留下来的又是什么。

## 三种层级

闭环优化修当前产物。

比如一张图手崩了，评估器发现问题，优化器改 `prompt`、换参考图、重跑局部区域。当前镜头变好了，但系统状态没有变化。下一集再遇到同类场景，它可能继续犯同样的错。

进化修改系统能力。

比如系统把这次失败沉淀成新的检查点、模板、资产库、反例集或 `skill`。下一次生成连续镜头前，它会先检查角色生命周期、服装状态、场景光源和上一镜头动作延续。经验被写进系统结构，下一次少走一点弯路。

自进化修改系统“如何改进自己”的能力。

这句话容易被讲玄。它不是系统有了生命，也不是不需要外部反馈。外部反馈当然可以进入系统，但它只是原料。更接近自进化的地方在于，系统开始观察自己的改进过程：哪些建议只是补丁，哪些建议能形成稳定策略；哪些问题应该改 `prompt`，哪些问题应该改资产结构；哪些失败来自生成器，哪些失败其实来自评估器看错了。

可以粗略分成三层：

```text
闭环优化：把这一次做对
进化：让下一次更不容易错
自进化：让系统更会发现、判断和固化“怎么变好”
```

元评测就在第三层附近。

评估器被元评测指出误判，然后变得更可靠，这叫评估器进化。可是元评测自己的反馈也有高低之分。差的反馈会说“这里被 `hack` 了，加一条规则挡住”。好的反馈会说“评估器把格式合规误判成任务完成，应该拆成事实一致性、用户意图满足、交付格式三个职责，并补反例”。如果系统开始比较这些元反馈的长期效果，把稳定做法沉淀成元评测策略、回归样例和评估器设计原则，才真正摸到自进化的边。

## 关系不是三角形，而是生产关系

生成器、评估器、优化器不是平级贴在白板上的三个框。它们像一条生产关系。

生成器决定系统能尝试什么。没有足够多样、受约束的候选，评估器再聪明，也只能在烂选项里挑一个不太烂的。

评估器决定系统能看见什么。它只看单帧美感，就会放过跨镜头漂移；它只看格式，就会放过事实错误；它只看平均分，就会放过关键红线。

优化器决定系统会怎么改。弱优化器只会重跑。稍好一点的优化器会改参数和参考图。更成熟的优化器会把问题归因到流程、资产、任务契约和评估标准上。

所以系统演化要看状态落在哪里：

| 改动位置 | 说明 | 层级 |
| --- | --- | --- |
| 当前产物 | 改一段文案、一张图、一个镜头 | 闭环优化 |
| 生成策略 | 改 `prompt`、模板、上下文选择、工具默认值 | 进化 |
| 评估策略 | 新增检查点、反例集、结构化评分、质量网关 | 进化 |
| 优化策略 | 改返工路线、资产规范、职责拆分、任务契约 | 进化 |
| 元策略 | 改“如何发现问题、归因问题、固化经验、验证改动” | 自进化 |

这也是我在 [[Agent-Native]] 里说的那件事：产品不是接入一个会聊天的模型就智能了。真正的智能闭环要能观察失败、修正交付，并把修正沉淀回生产系统。

## `AI` 漫剧链路里的对象映射

公开资料里，`AI` 漫剧的真实生产已经不是“写一句提示词生成一集”。更常见的链路是：

```text
IP / 选题
  -> 剧本改编
  -> 故事蓝图
  -> 角色、服装、场景、道具资产
  -> 分镜 / 故事板
  -> 静帧 / 参考生视频
  -> 视频生成与选片
  -> 配音、音效、字幕、剪辑
  -> 发布
  -> 数据复盘
```

小云雀这类短剧 `Agent` 产品会从标准剧本出发，生成故事蓝图、角色设计和分镜，并允许人工继续编辑角色与分镜。`Vidu` 这类视频模型则把“参考生视频”和主体库放到更靠前的位置，用多参考素材提升角色和场景连续性。腾讯云开发者社区的行业文章也把漫剧生产拆成剧本、分镜、素材、视频生成、后期剪辑和发行运营几段，说明这件事已经更接近一条生产线，而不是单点生成工具。[^xiaoyunque] [^vidu] [^tencent-cloud]

放进三个对象后，每一段都能看清楚。

### 剧本层

`Generator` 是剧本改编 `Agent`。它把小说、网文、原创大纲改成短剧脚本，拆集、写钩子、改台词。

`Evaluator` 看节奏、爽点、人物动机、平台尺度和可视化难度。很多文字在小说里能成立，到了漫剧里就不行。长心理活动、复杂群像、抽象设定，都可能变成视频生成的负担。

`Optimizer` 会删复杂场面，把心理描写改成动作，把多人争吵拆成更短的单人镜头，把“他很痛苦”改成“他盯着碎掉的杯子，半天没有弯腰去捡”。

这里的进化不是剧本越写越花，而是系统越来越懂什么内容适合被后面的图像和视频模型生产。

### 资产层

`Generator` 生成角色、服装、场景、道具和风格参考。

`Evaluator` 检查角色是否可复用，服装是否稳定，场景是否支撑多集使用，画风是否统一，是否有版权风险。

`Optimizer` 补角色三视图、表情表、服装状态、年龄阶段、常用姿势和命名规范。角色不再只是“一张好看的图”，而是跨镜头、跨集复用的生产资产。

这一层特别能体现进化。一个项目做完后，如果只留下成片，系统没有长多少；如果留下角色资产库、场景库、失败样例和风格规范，下一部作品就站在前一部的肩膀上。

### 分镜层

`Generator` 把剧本拆成镜头：景别、角色位置、动作、表情、台词、画面重点。

`Evaluator` 检查镜头是否讲清楚，情绪是否接得上，角色位置有没有跳，是否出现视频模型难以处理的多人同框和复杂动作。

`Optimizer` 会补反应镜头、拆短镜头、固定镜头词、减少过度运镜，把高风险镜头提前标出来。

很多漫剧返工发生在视频层，但病根在分镜层。分镜没有记录上一镜头的姿态和情绪，后面再怎么补 `prompt` 都像在漏水的地方贴胶带。

### 视频层

`Generator` 是图生视频、文生视频或参考生视频模型。

`Evaluator` 看脸部漂移、闪烁、口型、肢体、运镜、动作连续性、画面信息是否服务剧情。

`Optimizer` 会换参考图、缩短镜头、降低运动幅度、局部重跑、增加关键帧，或者把一个复杂镜头拆成两个安全镜头。

这一层的闭环优化最容易被看见，因为每次重跑都有直观结果。但如果所有优化都停在这里，成本会越来越高。视频层应该修视频层的问题，不应该替剧本、资产和分镜背锅。

### 后期与发行层

`Generator` 生成配音、音效、字幕、封面、标题和多个剪辑版本。

`Evaluator` 看节奏、完播率、前三秒留存、违规风险、评论反馈和平台推荐表现。

`Optimizer` 改标题封面、重剪节奏、替换配音情绪、调整开场信息密度，也可能反向影响下一集的剧本结构。

发行数据是很强的外部反馈，但它不天然等于自进化。只有当系统能把数据转成可复用策略，比如“某类冲突适合前置到第一个镜头”“某类角色出场需要更强视觉锚点”，并且在后续项目里验证这些策略，数据才变成系统能力。

## 一个完整例子：角色漂移

假设第 8 集里，男主在医院走廊连续出现三次。第一镜是黑色外套，第二镜变成灰色风衣，第三镜脸型也变了。

闭环优化会这样做：

```text
发现漂移
  -> 补参考图
  -> 改 prompt
  -> 锁 seed 或换模型
  -> 重跑第二、三镜
```

当前镜头可能修好了。

进化会继续往前追：

```text
把问题归档为“同场戏角色状态漂移”
  -> 增加角色状态检查点
  -> 建立医院走廊场景的固定镜头词
  -> 在分镜模板里要求填写服装状态
  -> 把失败镜头加入反例库
```

下一次同场戏生成前，系统会先检查角色状态。

自进化会再追一层：

```text
统计多部作品的返工记录
  -> 发现漂移集中发生在“跨场景切换后返回同一角色”
  -> 判断旧优化策略过度依赖视频层重跑
  -> 在剧本到分镜之间新增角色生命周期表
  -> 让评估器比较“有状态表”和“无状态表”的返工率
  -> 通过后把它固化进生产流程
```

这里最重要的变化，不是多了一条规则，而是系统学会了把问题从“镜头坏了”重新归因到“状态没有被生产系统保存”。这就是生产关系变了。

## `skill` 在这里放在哪里

`skill` 适合承载进化，但不要把它神化。

一次返工经验可以变成一个 `skill`：

```text
连续角色镜头生成 skill
  - 输入：角色卡、角色状态表、场景、分镜
  - 步骤：先锁服装和情绪，再生成静帧，再做视频
  - 检查：脸、服装、姿态、动作延续、场景光源
  - 失败处理：局部重跑、拆镜头、回退到资产层修正
  - 验收：三镜连续播放无明显漂移
```

但 `skill` 本身只是文件夹、规则、脚本和资源的组合，和我在 [[Claude Code Skill 不过是一个文件夹？]] 里的判断一致。它不是智能的来源，只是经验被组织后的形态。

`skill` 的进化，是从临时手法变成稳定流程。

`skill` 的自进化，则要看系统能不能发现哪些 `skill` 经常失败，哪些步骤多余，哪些检查点漏判，哪些反例应该加入。更直接地说，系统不只是调用 `skill`，还要能维护 `skill`。

## 一条实用分界线

判断一个 `AI` 生产系统有没有进化，不要听它说自己用了多少模型。看它如何处理失败。

如果失败只导致重跑，这是闭环优化。

如果失败会留下检查点、资产规范、流程模板和反例库，这是进化。

如果系统开始评估自己的评估方式、返工方式和经验沉淀方式，并能用后续项目验证改动有效，这是自进化。

`AI` 漫剧只是一个容易看见的例子。保险报告、代码生成、投研分析、客服问答也是同一回事。生成器负责尝试，评估器负责看见，优化器负责改变。系统真正长出来的东西，藏在那些失败之后还被保留下来的结构里。
