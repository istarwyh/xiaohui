一张客服工单只有一句：“信用卡被扣了两次，已经三天没人处理。”

普通大模型读完，可能先道歉，再解释原因，最后写一段处理建议。业务程序等的却是几个字段：交给账单组还是技术组，有多紧急，能不能自动退款。

`Jev` 不写那封信，只填答题卡。

这款模型由 `TypeSafe AI` 在 2026 年 9 月发布。官方称它为第一个 `System One Model`：输入一份状态和若干问题，输出 `Choice`、`Score`、`Noul` 三种带概率的判断。模型闭源，也没有公开论文。没人能从外面看见它的网络结构和训练配方。下文只根据接口、速度和重复调用表现，拼出一种可能的实现。

## 最容易想到的实现：换掉写作出口

`Transformer` 读完一段文字后，内部表示是一组上下文化向量。[[Transformer|向量为什么能够表示语义]] 详细梳理了这些向量怎样产生。

`GPT` 会把向量乘上一个词表矩阵，得到下一个 `token` 的概率：

$$
P(token)=softmax(HW_{vocab})
$$

选出的 `token` 会被送回模型，继续预测下一个。为了回答“账单组还是技术组”，模型仍要一个词一个词地写出 `billing`，再让程序解析字符串。

一种朴素的猜法，是让 `Jev` 跳过这段路，在隐藏向量后接一个判别出口：

$$
H=Transformer(state, question, criteria)
$$

$$
s_i=g(H,c_i),\qquad P(c_i)=softmax(s_i)
$$

$c_i$ 是候选项。在这个假设里，模型分别计算“账单问题”“技术故障”“销售咨询”与当前工单的匹配分数，再一次性给出概率。

三种官方接口都可以用这套旧工具解释：

- `Choice` 可以按多分类处理，对候选项做 `softmax`。
- `Noul` 可以按二分类处理，用 `sigmoid` 输出某句话为真的概率。
- `Score` 可以按有序分类处理，先判断各档分数的概率，再计算一个落在两档之间的期望值。

十年前的 `BERT` 分类器已经会读取 `[CLS]` 向量，再接一个分类头。`Jev` 对外表现出的差别在候选项里。

传统分类器在训练时就把标签焊死了。垃圾邮件模型判断垃圾邮件，风控模型预测违约。`Jev` 的接口允许调用者临时传入问题描述和候选项：今天分工单，明天挑工具，后天检查一段 `Agent` 轨迹。假如它在这些任务上都能工作，模型学到的就不只是某一组标签，还包括“根据自然语言描述做一次有限判断”。

从产品接口看，它像一个可以现场换题的通用判别模型。至于内部是否真用了一个传统意义上的判别头，公开资料还不能回答。

## 判别头不会凭空读懂退款

随机初始化一个 `Transformer`，再接上判别头，它不会突然理解退款、权限和代码风险。若 `Jev` 确实能处理调用时才写下的问题，它的主干必然通过训练获得了相当多的语言知识。

一种说得通的路线，是先用大规模语料获得通用表示，再用判别任务和概率校准做后训练：

```text
大规模语义预训练
  -> 能读懂状态、问题和候选项的 Transformer
  -> Choice / Score / Noul 判别训练
  -> 概率校准与 RLCD
  -> 面向程序的结构化接口
```

第一步未必是标准的下一个 `token` 预测，也可能包含掩码预测、对比学习、蒸馏或混合目标。`TypeSafe AI` 只公开了“新架构”“并行采样器”和 `RLCD` 这些名字，没有给出足以复现的训练细节。产品接口只能说明它怎样收题、怎样交卷，不能证明它在训练时走过哪条路。

“用基础模型时代的训练办法，造一个通用判别模型”可以当作工作假设，不能当作厂商已经证实的事实。

## 省下逐个 `token` 等待的时间

生成模型必须按顺序写出答案。哪怕程序只要一个枚举值，前一个 `token` 没出来，后一个也不能开始。

判别模型读完输入，直接按下几个按钮：

```text
生成模型：读输入 -> token 1 -> token 2 -> ... -> JSON 解析

判别模型：读输入 -> 全部概率
```

多个问题如果共享同一份 `state`，实现者还可能复用状态表示，并行计算后面的判断。取消自回归解码、复用输入表示、缩小输出空间，已经足以解释一部分速度和价格优势，不必先假定它发明了全新的模型结构。

它仍然要读输入。合同塞进几十万字，`Attention` 的计算不会凭空消失；任务需要搜索资料、调用工具或走十步推理时，一次前向计算也补不回缺失的过程。官方宣传的几十倍、几百倍差距，只适用于形状合适的短判断，不能外推成所有智能任务都便宜了同样多。

## 概率会晃，但未必是模型在随机采样

如果线上 `Jev` 使用固定权重、固定计算图和确定性推理，相同输入的概率应该几乎不动。普通浮点误差很难解释 `0.43` 变成 `0.53`。

`TypeSafe` 自己做过一次自一致性实验。同一份保险理赔材料和十四个问题运行十五次，`Jev` 每个问题的平均标准差为 `0.0102`，其中一个问题在 `0.43—0.53` 之间变化，跨过了 `0.5`。那次实验为每轮请求加入了不同的无意义 `uid`，不算字节完全相同，却暴露了模型对无关字段的敏感性。

另一份独立实验固定 `jev-1.13.0`，重复发送字节相同的请求。两组各一百个样本里，最终判断分别有 `2%` 和 `1%` 翻转，概率分布的平均变化约为 `0.01`。这已经不是“最后几位小数是否一致”的争论。

这组结果不能证明 `Jev` 内部采用了哪种架构。并行采样、随机专家路由、多路径集成、近似计算会造成波动，服务端模型更新、请求路由和推理配置变化也会。闭源条件下甚至无法判断抖动发生在模型里，还是模型外面的服务栈里。

调用者只能把返回概率当作一次测量，而不是刻在数据库里的事实。产品是否可用，要看它跨越业务阈值的频率，不能只看平均波动。

## 适合它的任务，答案要能提前列出来

这类模型先天受答案空间约束。工单可以提前列出几个部门，文章却无法提前列出每一句话。输入需要理解自然语言、答案又能装进有限格子时，它才有机会省下生成模型的成本。

| 工作形状 | 更合适的工具 | 原因 |
| --- | --- | --- |
| 规则明确，输错代价高 | 普通代码、规则引擎 | 可复现、可审计，不需要模型猜 |
| 语义模糊，但答案空间有限 | `Jev` 一类判别模型 | 能理解自然语言，又不用生成长文本 |
| 需要查资料、多步推理、解释或创作 | `LLM`、`Agent` 或人工 | 答案无法提前装进几个格子 |

适合交给它的是大量、低风险的小判断：

- 把工单路由到有限的部门；
- 从一组候选工具或资料中做粗排；
- 给内容、风险和紧急程度打分；
- 检查 `LLM` 输出是否值得进入下一步；
- 给 [[如何科学评测 Agent 生成的文本报告：从评分体系到评测器的元评测|Agent 评测]] 提供一个低成本信号；
- 在批处理流水线里筛掉明显样本，把少数模糊样本交给昂贵模型或人。

如果任务已经积累了稳定标签和大量训练数据，一个小型 `Encoder`、`XGBoost` 甚至几条 `SQL` 规则可能更便宜、更稳。`Jev` 的卖点不在于重新发明分类，而在于任务刚出现、标签随调用变化，团队又不想为每个判断单独训练模型。

这些工作不该直接交给它：

- 正确答案可能根本不在候选项里；
- 判断之前必须搜索新信息或调用外部工具；
- 需要给出推理依据、报告或面向人的表达；
- 一次错误会直接转账、删数据、封账号或拒赔；
- 相同输入必须在几年后得到完全相同的结果。

有限输出可以挡住第四个部门，却不能保证前三个部门选得正确。

## 概率后面还要装保险丝

把单次概率直接接到业务按钮上，只要三行代码：

```python
if probability >= 0.5:
    approve_refund()
```

更稳妥的系统会留下拒绝区间。下面的数字只是示意，真实阈值必须从自己的业务样本中测出来：

```python
if probability >= 0.85:
    auto_accept()
elif probability <= 0.15:
    auto_reject()
else:
    route_to_rules_llm_or_human()
```

生产代码还要记录实际模型版本、完整问题和返回概率。同一笔业务重试时复用第一次结果，不再请求一次。高风险动作仍要经过确定性规则、权限校验和人工确认。[[如何打造可靠的Agent系统|可靠的 Agent 系统]] 讨论的正是这种边界：不稳定的部件只能在护栏内活动。

`Jev` 更像装在流水线上的语义传感器：看一眼材料，拨动几根指针。它可以建议那张客服工单去账单组，也可以报出 `0.91`。退款按钮前面仍要留一只真正的保险丝。
